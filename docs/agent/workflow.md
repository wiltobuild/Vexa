# Workflow

_How work moves through Vexa. Generated by /bootstrap-project on
2026-09-27; referenced by /start-task on every task._

## Modes

- **GUIDE** — default during bootstrap and at the start of a task: ask
  questions, explain options, recommend a workflow. No spawning, no writes.
- **COORDINATE** — after the user approves a task's workflow/plan: spawn
  read-only role agents (Argus, Athena, Themis, Apollo), validate their
  output, prepare the builder handoffs. Still no production writes.
- **EXECUTE** — only within an approved task, only for the approved scope:
  run the builder handoffs, run verification commands. Anything outside the
  approved scope drops back to GUIDE.

## Dual-builder, cross-review model (standing override)

This project overrides the global single-Codex-implements default (see
[decisions.md](decisions.md), 2026-09-27). For any task that reaches
EXECUTE:

1. **Athena splits the approved plan into ≤2 independently-scoped tracks**
   whenever the work is large enough to parallelize — pick a seam that
   minimizes shared-file collisions (e.g. backend service vs. frontend
   client, or two separate services/packages). Define the contract between
   tracks (shared types in `packages/shared`, an API/event shape) *before*
   either builder starts, since both need it simultaneously.
2. **Both builders run at the same time:**
   - Track A → a Sonnet subagent (via the `Agent` tool).
   - Track B → Codex CLI (via `codex exec`, using the handoff template).
3. **Cross-review, never same-model:**
   - Codex reviews Track A's diff (the Sonnet-built track) as Themis.
   - A Sonnet subagent reviews Track B's diff (the Codex-built track) as
     Themis.
   - Each reviewer gets the task brief, acceptance criteria, and the diff —
     not the other builder's own explanation of what they did.
4. **If a task is too small to split** (e.g. a one-file fix), one model
   builds it and the *other* model reviews it. Still never self-review.
5. **Apollo verifies the integrated result** — both tracks merged locally,
   build/typecheck/tests run, and for anything user-visible or real-time
   (voice, gateway, UI), exercised against a real local server per
   "Verification depth" below.
6. Must-fix findings from either reviewer go back to the track's own
   builder, not to the other builder and not fixed by the reviewer/Claude
   directly.

## Standard workflow by task type

| Work type | Workflow |
|---|---|
| Small, low-risk fix | Argus → one builder (Codex or Sonnet) → the *other* model as Themis → Apollo |
| Feature | Argus → Athena (split into tracks) → **approval** → parallel Sonnet+Codex builders → cross-review (Codex reviews Sonnet, Sonnet reviews Codex) → Apollo |
| UI change | Argus → Athena → **approval** → builder(s) → cross-review → Apollo (visual/runtime check in the browser pane) |
| Database/migration | Argus (+ data-integrity check) → Athena → **approval** → one builder (schema changes are hard to split safely) → other-model Themis review → Apollo (runs the migration against real local Postgres) |
| Audit / harsh review | Parallel Argus + Themis specialists → dedup → user |
| Docs only | Argus → writer → Themis |
| Architecture change (e.g. mediasoup/SFU introduction) | Argus → Athena → independent Themis review → **approval** |

Bold **approval** = hard stop; do not proceed without explicit user sign-off.

## Builder handoffs

- **Codex track**: delegated via `codex exec` using the handoff template in
  `~/.claude/skills/start-task/templates/handoff-codex.md`.
- **Sonnet track**: delegated via the `Agent` tool (subagent_type: `claude`
  or `general-purpose`, `model: sonnet`), given the same shape of brief
  (approved plan reference, exact scope, constraints, expected result
  format) as the Codex handoff template, so both tracks are held to the
  same bar.

Both the handoff prompt and the resulting diff are shown to the user — the
handoff itself does not require a separate approval step beyond the plan
approval that already authorized this phase of work, but the diff is
reviewed (by the other model, then by Apollo) before anything is committed.

## Verification depth

**Unit + runtime/browser**, not unit-only. Docker is confirmed available on
this authoring host (`docker 29.7.2`, `compose v5.3.1`), so:

- Run `pnpm typecheck`, `pnpm test`, `pnpm build` locally, not just in CI.
- For backend/gateway work: start the real local stack
  (`docker compose up -d`, `pnpm db:migrate`, `pnpm dev:all`) and run the
  integration suites (`VEXA_INTEGRATION=1 pnpm --filter @vexa/gateway test`,
  `VEXA_INTEGRATION=1 pnpm test:e2e`) against real Postgres/Redis/API/
  gateway — not mocked.
- For UI/runtime work: use the built-in browser pane against the real local
  dev server per the verification workflow in the system prompt.
- For voice/media work specifically: the delivery plan's own exit gate is
  "two authenticated browsers... exchange real audio" — do not claim this
  phase passes without actually driving two real peer connections.

## Git / commit strategy

- Feature branch per task, PR into `main`, no direct pushes to `main`.
- Small commits per reviewable unit (per builder track where practical).
- Both cross-reviewers must accept (or have their findings resolved) before
  a PR is proposed for merge.
- Merging a PR into `main` is a shared/public action — confirm with the
  user before each merge, per the global safety rules, even though the
  branch→PR→merge pattern itself is pre-approved as standing practice.

## Data safety policy

- No irreplaceable data exists yet — local Postgres via Compose only.
- Preserve the existing tracked-migration safety (checksums + advisory
  locking, from PR #15/#2) for every schema change: no reverting to
  whole-schema replay.
- Once Phase 2 (real accounts) begins and real user data exists, require a
  verified backup before any destructive migration — revisit this policy
  explicitly at that point rather than assuming current low-risk defaults
  still apply.
